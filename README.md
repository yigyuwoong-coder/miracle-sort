# Miracle Sort

> 태양 입자가 내 메모리의 비트를 뒤집어, 배열이 저절로 정렬될 때까지 기다리는 **미라클 소트** 시뮬레이션.
> 태양계를 시뮬레이션할 때 가장 무거운 계산인 충돌 판정을 **공간 해싱**으로 개선하고, 그 효과를 실측했다.

- 시뮬레이션: `index.html`
- 해싱 성능 측정: `bench.html`
- **사이트: https://yigyuwoong-coder.github.io/miracle-sort/**
- 해싱 성능 측정 페이지: https://yigyuwoong-coder.github.io/miracle-sort/bench.html

```js
function miracleSort(a) {
  while (!isSorted(a)) {
    // 아무것도 하지 않는다. 태양 입자가 비트를 뒤집어 정렬해 주길 기다린다.
  }
}
```

## 화면

- **지금**: 시뮬레이션 안에서 흐른 시간. 지구가 태양을 한 바퀴 돌면 1년이다.
- **배속**: 아래 띠의 버튼으로 고른다.
  - *정밀 계산* (1주/초, 1달/초, 최대): 태양풍 입자 하나하나의 이동과 충돌을 2.8시간 간격으로 모두 계산한다. 빠른 배속에서도 계산은 한 스텝도 건너뛰지 않고, 화면만 프레임마다 한 번 그린다.
  - *천문 시간* (1천 년/초 ~ 1조 년/초): 비트가 뒤집히는 순간들만 정확히 계산한다(아래 설명).
  - *해금 배속* (10⁵²~10⁵⁰⁰년/초, 잠김): 아래 "해금 배속" 참고.
- **내 메모리**: 16비트부터 2048비트(2~256바이트)까지 13가지. 128비트까지는 막대(값)와 8비트 칸을, 그보다 크면 막대만 보여 준다. 방금 뒤집힌 비트(원소)는 금색, 정렬되면 모두 초록색이 된다.
- **공유하기 / 결과 공유**: 정렬에 성공(기적)한 뒤에만 열린다. 카드에 정품인증 도장과 인증 코드가 찍히고, 공유 링크로 누구나 진위를 확인할 수 있다(아래 "정품 인증"). 비트 수, 걸린 시간, 정렬된 배열, 천문학적 비교 멘트가 담긴 결과 카드(1080×1350 PNG)를 *이미지 저장*, *공유하기*(휴대폰에서는 카카오톡 등으로 바로 공유), *링크 복사*할 수 있다. 비트 수가 클수록 등급이 올라가고(일반 → 희귀 → 영웅 → 전설 → 신화 → 초월 → 우주) 반짝이·빛줄기·글로우·은하 소용돌이가 늘어난다. 공유 링크(`?bits=64`)로 열면 같은 비트 수로 시작한다.
- **해금 배속 🔒**: 1항하사(10⁵²)·1무량대수(10⁶⁸)·1구골(10¹⁰⁰)·1센틸리언(10³⁰³)·1구골⁵(10⁵⁰⁰) 년/초. 잠겨 있어서 누르면 개발자 후원 창이 뜬다. 해금 코드는 4단계이고, 앞 단계 코드가 다음 단계 코드의 앞부분이라 끝까지 치면 차례로 열린다. 화면 어디서나 키보드로 치거나(한/영 무관) 후원 창에 입력한다. 코드는 공개 소스에 그대로 두지 않고 SHA-256 해시값만 저장해 비교한다(`js/unlock.js`). 계산 방식은 아래 "해금 배속"을 참고.
- **충돌 판정 1스텝 · 실측** (오른쪽 위): 지금 화면에 있는 입자·소행성 그대로, 해싱을 쓸 때와 안 쓸 때의 충돌 판정 시간을 2.5초마다 별도 스레드에서 잰다. "시뮬레이션에 해싱 사용"을 끄면 정밀 계산이 실제로 그만큼 느려진다.

## 어떻게 동작하나

1. 태양이 매 스텝 태양풍 입자를 내보낸다(초속 300~700km, 거의 등속 직선).
2. 수성·금성·화성과 소행성대(3,000개)는 입자를 막는다. 충돌 판정에 **공간 해싱**을 쓴다(아래).
3. 지구에 닿은 입자는 아주 드물게 메모리의 무작위 비트 1개를 뒤집는다(Single Event Upset).
4. 배열이 오름차순이 되는 순간이 기적이다. 그 시각을 기록하고 멈춘다.

### 비트는 얼마나 자주 뒤집히나

지상 메모리의 소프트 에러율, 즉 **비트 하나가 1시간에 뒤집힐 확률 10⁻¹²** 을 썼다(1,000 FIT/Mbit). 이 값은 예전 실험실 측정들(200~5,000 FIT/Mbit)의 중간이다. 서버 현장 측정에서는 이보다 1,000배 이상 낮게 나온 결과도 있다. 시간은 지구가 한 바퀴 돌면 1년이다.

| 메모리 | 비트 하나가 뒤집히는 주기 (평균) | 기적까지 (평균) |
|---|---:|---:|
| 32비트 | 약 357만 년 | 약 4.3억 년 |
| 48비트 | 약 238만 년 | 약 56억 년 (지구 나이보다 길다) |
| 64비트 | 약 178만 년 | 약 1,700억 년 (우주 나이의 12배) |
| 80비트 | 약 143만 년 | 약 6조 년 |
| 512비트 | | 약 10⁹¹년 |
| 2048비트 | | 약 10⁴⁶⁹년 |

"처음 정렬될 때까지 필요한 플립 수"는 무작위 배열이 정렬돼 있을 확률(C(N+255, N)/256ᴺ)의 역수보다 2~7배 크다. 정렬된 상태들이 서로 몰려 있기 때문이다. 표의 값은 비트를 직접 뒤집어 보는 몬테카를로로 구했다.

> 참고: 실제 지상의 비트 플립은 주로 우주선(cosmic ray)이 대기와 부딪혀 만든 2차 중성자 때문이고, 태양 활동이 강할 때 늘어난다. 이 사이트는 이를 "태양 입자가 지구에 닿는 것"으로 단순화했다.

### 비트 플립은 시드로 정해진다 (재현·검증 가능)

비트 플립은 평균 빈도가 일정한 포아송 과정이다. 그래서 플립 시각(지수분포 간격), 어느 원소의 어느 비트인지, 몇 번째 플립에서 정렬되는지가 **처음 정한 시드의 난수열로 전부 정해진다**(`js/sim/flips.js`). 배속을 어떻게 바꾸든, 화면을 껐다 켜든 같은 시드면 같은 기적이 같은 시각에 난다.

- 기적과 기적 사이 한 구간에서는 플립을 **2,000만 번까지 하나씩 정확히** 센다. 80비트 이하는 거의 항상 이 안에서 기적이 난다.
- 그 안에 정렬되지 않으면(96비트 이상) 남은 대기 시간을 지수분포로 근사한다. 이것도 "대충 계산"이지만 시드로 정해진다. 평균 = c(N) / 정렬확률 플립이고, c는 몬테카를로 보정값이다.
- 화면의 입자는 같은 평균 빈도를 눈으로 보여 주는 역할이다. 평균 빈도는 지구 피격 빈도 × 현실 에러율로 보정했다.

### 해금 배속 (1항하사 ~ 1구골⁵ 년/초)

- 정확히 셀 수 있는 플립은 시간 예산 안에서 하나씩 센다. 한 구간이 2,000만 플립을 넘으면 위의 대충 계산으로 기적 시각을 바로 구한다.
- 컴퓨터 실수(double)는 약 10³⁰⁸까지만 담을 수 있다. 그래서 **10²⁹⁰년을 넘으면 시간을 log10으로 저장**하고 "1.6 × 10⁴⁶⁸년"처럼 표시한다.

| 메모리 | 바로 기적이 나는 배속 |
|---|---|
| 256비트 이하 | 1항하사(10⁵²) 년/초 |
| 512비트 | 1구골(10¹⁰⁰) 년/초 |
| 1024비트 | 1센틸리언(10³⁰³) 년/초 |
| 2048비트 | 1구골⁵(10⁵⁰⁰) 년/초 |

### 정품 인증 (위조 방지)

정적 사이트는 모든 코드가 브라우저에서 돌아가서, 개발자 도구로 그림 함수를 직접 부르는 것 자체는 막을 수 없다. 해금 단계도 마찬가지로 풀 수 있다. 대신 **가짜는 바로 들키게** 했다.

- 결과 카드에는 **인증 코드**(`비트-시드-몇번째기적-검증값`)와 **정품인증 도장**이 찍힌다. 검증값은 결과(플립 수·정렬된 배열)의 SHA-256 앞 8자리다(`js/cert.js`).
- 공유 링크(`?cert=코드`)를 열거나 "진위 확인"에 코드를 넣으면, 사이트가 그 시드로 **처음부터 다시 계산**해 검증값을 비교한다(`js/cert-worker.js`, 최대 1~2초). 맞으면 다시 그린 진짜 카드와 함께 "✓ 정품 인증"을 보여 준다.
- 숫자를 고친 이미지는 코드가 맞지 않거나, 다시 계산한 진짜 결과와 숫자가 달라서 드러난다.
- 해금으로 배속을 높여도 결과는 시드로 정해지므로 결과를 조작할 수는 없다. 빨리 볼 수 있을 뿐이다.

### 결과 카드 디자인

- 비트 수가 클수록 등급이 오르고 더 화려해진다(일반 → 희귀 → 영웅 → 전설 → 신화 → 초월 → 우주). 반짝이 수, 빛줄기, 글로우, 홀로그램, 은하 소용돌이가 늘어난다.
- 인증 코드마다 디자인이 다르다. 성운 색 6가지, 장식 2개(고리 행성·초승달·혜성·별자리 중), 반짝이 모양(네 갈래·여섯 갈래·다이아·빛망울), 막대 모양 3가지 중에서 고른다. 같은 코드면 언제 그려도 같은 카드다.

### 화면을 꺼도 흐르는 시간

브라우저는 화면이 꺼지거나 탭이 가려지면 페이지를 멈춘다. 그래서 돌아왔을 때 꺼져 있던 실제 시간 × 배속만큼 우주 시간을 한 번에 따라잡는다. 그동안은 그릴 필요가 없으므로 입자 대신 비트 플립 사건만 센다. 그사이 기적이 났으면 그 연도로 기적 창이 뜬다. 일시정지 중에는 흐르지 않는다.

## 공간 해싱

### 문제

매 스텝 입자 P개(약 4,000개)가 소행성 M개(3,000개) 중 하나에 부딪혔는지 확인해야 한다. 입자마다 소행성을 전부 확인하면 **O(P·M)**, 한 스텝에 약 1,200만 번 비교한다.

### 해결: 해시 테이블에 소행성을 칸별로 넣어 두기

1. 공간을 한 변 h인 정사각형 칸으로 나눈다. 소행성의 칸 좌표는 `(⌊x/h⌋, ⌊y/h⌋)`이다.
2. 칸 좌표를 **해시 함수**로 버킷 번호에 대응시킨다.
   ```
   h(cx, cy) = (cx · 73856093  XOR  cy · 19349663)  mod  테이블크기
   ```
   큰 소수를 곱해 섞는 고전적인 공간 해시 함수다. 테이블 크기를 2의 거듭제곱으로 잡아 mod를 비트 AND로 계산한다.
3. **충돌 처리는 분리 연결법(chaining)** 으로 한다. 연결 리스트를 객체로 만들지 않고 배열 두 개(`head[버킷]`, `next[원소]`)로 표현한다. 넣을 때는 버킷 맨 앞에 끼운다(O(1)).
4. **부하율**(원소 수 / 버킷 수)이 0.5 이하가 되도록 테이블 크기를 정한다.
5. 입자는 자기 칸과 주변 8칸, 즉 버킷 9개만 확인한다. 서로 다른 칸이 같은 버킷에 들어가는 해시 충돌이 있어도, 실제 거리를 다시 계산하므로 결과는 정확하다.

테이블을 짓는 데 O(M), 조회는 입자당 평균 O(1)이므로 한 스텝이 평균 **O(P + M)** 이다. 소행성이 움직이므로 테이블은 매 스텝 새로 짓는다.

### 정확성을 위해 신경 쓴 점

- **이동 구간 충돌 판정**: 입자는 한 스텝에 0.02~0.05 AU를 움직이는데, 소행성 반지름은 0.002~0.008 AU다. 스텝 끝 위치만 보면 입자가 소행성을 뚫고 지나간다. 그래서 소행성 기준 상대 운동으로 본 **입자의 이동 선분과 원의 최단 거리**로 판정한다.
- **칸 크기**: h를 (입자 이동 거리의 절반 + 소행성 최대 반지름 + 소행성 이동 거리)보다 크게 잡았다. 그러면 이동 구간 중점의 칸과 주변 8칸만 봐도 충돌을 절대 놓치지 않는다.
- 해싱을 쓸 때와 안 쓸 때 전체 시뮬레이션 결과(지구 피격, 비트 플립, 살아 있는 입자 집합)가 완전히 같은지 테스트로 확인했다.

## 측정 결과

`node bench/run.mjs` (Node v24, Apple M4 Pro). 전체 결과는 [`bench/results-node.md`](bench/results-node.md)에 있다. 브라우저(`bench.html`, Chrome)에서도 비슷하게 나온다.

**시뮬레이션이 1초 동안 계산하는 우주 시간** (소행성 3,000개, 정밀 계산)

| 방식 | 1스텝 | 1초 동안 계산되는 시간 |
|---|---:|---:|
| 해싱 없이 (전수 검사) | 54.4 ms | 2.1일 |
| 공간 해싱 | 0.42 ms | 280일 |
| | | **×131** |

**충돌 판정 1스텝, 규모를 키우며** (입자 P = 10·M)

| 소행성 M | 입자 P | 해싱 없이 | 공간 해싱 | 빨라진 배수 |
|---:|---:|---:|---:|---:|
| 250 | 2,500 | 1.23 ms | 0.062 ms | ×20 |
| 500 | 5,000 | 5.88 ms | 0.13 ms | ×46 |
| 1,000 | 10,000 | 26.2 ms | 0.47 ms | ×56 |
| 2,000 | 20,000 | 121 ms | 1.55 ms | ×78 |
| 4,000 | 40,000 | 510 ms | 4.17 ms | ×122 |
| 8,000 | 80,000 | 2,098 ms | 12.2 ms | ×172 |

- M을 2배로 늘리면(P도 2배) 전수 검사는 약 4배 느려진다(O(P·M)). 해싱은 약 2~3.5배다. 규모가 클수록 격차가 벌어진다.
- 해싱이 정확히 2배씩이 아닌 이유: 소행성대 넓이는 그대로인데 소행성이 늘어나면 칸 하나에 든 소행성도 늘어나기 때문이다. 칸 크기를 밀도에 맞춰 줄이면 더 선형에 가까워진다.

측정 방법:
- 같은 시드(42)로 같은 입력을 만들어 두 방식을 비교한다.
- 첫 실행은 JIT 워밍업으로 버린다. 한 샘플이 4ms 이상이 되게 묶어 재서(브라우저 타이머 해상도 ≈ 0.1ms) 여러 번의 중앙값을 쓴다.
- 측정할 때는 전원을 연결하고, 다른 탭을 닫고, 측정 중에는 탭을 바꾸지 않는다.

- 빠른 입자가 작은 소행성을 뚫고 지나가는 경우를 이동 구간 판정이 잡는다.
- 공간 해싱과 전수 검사가 무작위 이동 구간 20만 개에 대해 같은 결과를 내고, 전체 시뮬레이션 300스텝도 똑같이 진행된다.
- 정렬 판정(뒤바뀐 이웃 쌍 수를 O(1)로 갱신)이 매번 전체를 다시 센 값과 같다.
- 정렬 확률 공식이 손 계산·몬테카를로와 맞고, 플립 수가 포아송 분포의 기대값과 맞는다.
- 기적까지 평균 시간이 독립 몬테카를로와 맞다.
- **재현성**: 화면처럼 들쭉날쭉 나눠 진행해도(최대 11만 조각) 처음부터 다시 계산한 결과와 플립 번호·배열·시각까지 같다. 화면(World)에서 난 기적도 같다.
- **인증**: 진짜 코드는 통과하고, 검증값을 1비트만 고쳐도 실패한다. 다른 시드로는 같은 검증값이 나오지 않는다.
- 2048비트를 10⁵⁰⁰년/초로 돌리면 로그 시간으로 10⁴⁶⁹년 근처에서 기적이 난다.
- 해금 코드 단계는 로컬 파일(`tests/codes.local.json`, 저장소에 올리지 않음)이 있을 때만 검사한다.

## 로컬 실행

ES 모듈과 Web Worker는 `file://`로 열면 동작하지 않아 간단한 서버로 띄운다(의존성 없음).

```bash
node tools/serve.mjs 8123
```

브라우저에서 `http://localhost:8123`을 연다.

## GitHub Pages 배포

빌드 과정이 없는 정적 사이트라 저장소에 올리기만 하면 된다.

1. GitHub에서 새 저장소를 만든다(예: `miracle-sort`, Public).
2. 이 폴더에서 다음을 실행한다.
   ```bash
   git init
   git add .
   git commit -m "Miracle Sort"
   git branch -M main
   git remote add origin https://github.com/<아이디>/miracle-sort.git
   git push -u origin main
   ```
3. 저장소 **Settings → Pages**에서 Source를 *Deploy from a branch*, Branch를 `main` / `(root)`로 두고 저장한다.
4. 1~2분 뒤 `https://<아이디>.github.io/miracle-sort/`에서 열린다.
